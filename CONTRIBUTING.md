# Contributing

The project recovers one maintainable engine with shared types, original
translation units where the evidence supports them, and behavior that matches
the reference build. Changes need both good source and a passing check.

## Before you start

- **Windows:** clone with `git clone -c core.longpaths=true <URL>`. Some
  Zero Hour reference paths exceed 260 characters and fail to check out
  otherwise.
- **What the clone does not contain:** the maintainers' generator; and
  the check service, the
  `boat-ok` label, issues and pull requests, which exist only on the GitHub
  repository. A first line such
  as `// Generated by gen_repo.py; map snapshot ...` only records that the
  file's skeleton and `FUNCTION` annotations were produced from the
  ledger. A `FUNCTION` annotation with no body below it marks an address
  that this file owns and nobody has written yet; put the body directly
  below the annotation and keep the annotation.
- **Reading the target:** `baseline/game.dat` is the original program,
  version 1.06 (its SHA-256 is in `baseline/README.md`). Read any function's
  bytes there with a disassembler, at the RVA from the worklist or ledger.
  In an issue or pull request cite the address, size, offsets and what the
  code does rather than pasting dumps. Do not add any other executable, game
  asset or byte or disassembly dump to the repository.
- **When Zero Hour and the reference build disagree,** the reference build
  decides behaviour. Zero Hour is evidence for names, types and shape only
  where the code corresponds. Note the difference in the pull request.
- **Commit messages:** a short imperative subject (72 characters at most);
  a body with the evidence (addresses, Zero Hour `path:line`, anything you
  inferred, marked as an inference); a `Removed-Declaration:` trailer for
  each declaration you delete. Commit with a public address or your GitHub
  no-reply address.
- **Attribution:** add the `NOTICE` line to a file when you copy or adapt
  any text from the Electronic Arts release, including code shape followed
  line by line and comments. Using a Zero Hour identifier as a name does not
  by itself require it. When unsure, add the line.
- **Where to ask:** open an issue in this repository. Start the title with
  `Evidence:`, `Path:` or `Ledger:` for a missing fact, a proposed header path
  or a ledger correction. Comments in the source sometimes mention notes the
  clone does not contain; treat those as history and ask in an issue.
- **Addresses:** an RVA is relative to the image base. A virtual address
  (VA) in a comment is the RVA plus `0x400000`. To find an RVA in
  `baseline/game.dat`, list its sections with `objdump -h baseline/game.dat`; for a VA inside
  a section, file offset = VA - VMA + "File off" of that section.
- **Line endings:** the repository stores LF. On Windows set
  `git config core.autocrlf input` (or `false`) in your clone so a patch does
  not convert whole files.
- **Removing or renaming a declaration:** add one
  `Removed-Declaration: Class::member` line per removed or renamed
  declaration (qualified identifier, one per line) to the tip commit message.
  The check names any it requires that are missing.
- **Checking without the reference compiler:** the reference toolchain is
  Visual C++ 7.1, which most contributors will not have. You can still
  compile a header with a compatible 32-bit x86 ABI C++ compiler and assert its layout
  (`static_assert`-style `typedef char check[sizeof(T) == 0x40 ? 1 : -1];`
  and `offsetof`) before you open a pull request. The pull-request check then
  compiles with the reference compiler. A member that no compiled function
  reads is not checked by anything, so state its evidence.
- **Words you will meet:** *Boat* is the cloud service whose compiler-only
  machines build pull requests; *the farm* is the set of those machines;
  **BFME II / Boat** is the status the check posts on a pull request. A
  `// cl: /O1` line at the top of a source file gives that file's extra
  compiler flags; leave it as it is. A generated `// FUNCTION:` line and its
  words (`tier`, `evidence=`, `hypothesis:`) are explained in
  [Read a generated annotation](docs/ledger-and-checks.md#read-a-generated-annotation).
- **Where the attribution line goes:** first line of the file, above any
  `// cl:` line, exactly as `NOTICE` gives it. Existing files that place it
  lower are not wrong; do not move theirs.
- **Header changes cost more:** every file that includes the header, directly
  or through other headers, is rebuilt and compared. Add to a shared header
  only what your change needs; an inline accessor that Zero Hour has is fine
  when it emits no code of its own, but say so in the pull request.
- **Worklist generator:** with no input flags, `python3 worklist/generate.py`
  refreshes only `draft_headers_in_use.tsv`, `draft_headers_unused.tsv` and
  `stand_in_types.tsv` (and requires `src/` and `include/` to be clean against
  `HEAD`); it leaves the function tables untouched. To confirm a finished
  function drops out of `unwritten_with_zero_hour_counterpart.tsv`, commit your
  source change, download `worklist/inputs/unwritten.tsv` from the `progress`
  branch, and regenerate into a temporary directory:

  ```sh
  out=$(mktemp -d)
  python3 worklist/generate.py --unwritten /path/to/unwritten.tsv --output "$out"
  ```

  See [Refresh the lists](worklist/README.md#refresh-the-lists) for the other
  input reports. If you run without `--output`, restore tracked files with
  `git checkout -- worklist/` and do not commit its output.

## A first contribution, step by step

A pull request finishes one file or replaces one Draft header. For a first
one, a single function is fine. Write it like the
[reference files](docs/reference-files.md), and compare your file against the
list at the end of that page.

1. Clone (on Windows with `-c core.longpaths=true`).
2. Open `worklist/files.tsv` and take a file near the top (few functions
   left, a `real` class header), or open
   `worklist/unwritten_with_zero_hour_counterpart.tsv` and take a row with
   `ready_at_snapshot=yes`, `reference_kind=def`, `body_check=none-found`
   and a small `size_bytes` (under about 100). Higher `link_referrers` means
   more of the rebuilt game is waiting for that function.
3. Search `src/` and `include/` for its RVA and name; the owning file has a
   `// FUNCTION:` line for it.
4. Read its bytes in `baseline/game.dat` at the RVA, and its Zero Hour body at
   `zero_hour_file:zero_hour_line`.
5. Claim the item before writing code: search upstream open PR descriptions with
   `gh pr list -R Open-BFME/BFME2-Rebuild --state open --search "<RVA or file>"`,
   then open a draft PR with your `Claim:` line or take an exclusive swarm
   assignment.
6. Write the body directly below its `// FUNCTION:` line, against the shared
   headers. Where Zero Hour and the bytes differ, follow the bytes. Commit your
   change on top of current upstream `main` with a message that gives the
   evidence.
7. Run the local source-rules check on the committed tree before pushing so you
   never spend a compiler run on a G1-G8 failure:

   ```sh
   python3 tools/gates/gate.py . <upstream-main-ref> HEAD --json /tmp/gate.json
   ```

   `gate.py` reads committed Git trees (not uncommitted working-tree files).
   Fix every finding until it **exits 0 and `/tmp/gate.json` reports
   `"status": "pass"`**. If you edited a header under `include/`, check syntax
   and `sizeof`/`offsetof` with a compatible 32-bit x86 ABI compiler first, and
   keep function bodies out of shared headers unless supported by retail
   evidence (unowned inline definitions or constructors emit unexpected code in
   every includer).
8. Mark the pull request **Ready for review** with the claim line
   (`Claim: src/path/File.cpp` for a file, `Claim: include/Draft/X.h` for a
   Draft, `Claim: 0x00ABCDEF` for one function) and the evidence, for example:

   ```text
   Claim: 0x003B0FD0
   SpecialPowerStore::findSpecialPowerTemplateByID, 71 bytes.
   Zero Hour: GameEngine/Source/Common/RTS/SpecialPower.cpp:286.
   Bytes against Zero Hour: <what agrees, what differs and which you followed>.
   Unconfirmed: <fields, slots or names you could not confirm, or "none">.
   ```

   Draft pull requests can run source rules, but **automatic Boat admission
   waits until the pull request is marked Ready for review** (maintainer-started
   comparisons are separate).
9. Read the **BFME II / Admission**, **BFME II / Boat**, and **BFME II / Landing**
   statuses and fix measured code refusals (at most three rounds).

## Choose and prepare a change

1. Start with the [worklist](worklist/README.md) and check the latest `main`.
   A small function family with real headers and a corresponding Zero Hour
   body makes a good first task. Draft promotion and resolving an evidence
   question are useful contributions too.
2. Search open pull requests for the relative virtual address (RVA), source
   file and class. An RVA is the offset from the reference executable's
   load base. Follow the [claim instructions](worklist/README.md#claim-an-item).
3. Search both `src/` and `include/` for a body, including an inline body
   in a header. Follow the [ledger lookup](docs/ledger-and-checks.md#find-a-row-and-its-owner)
   to the current owning file and accepted name. Compare the [Zero Hour
   source](reference/README.md) with the target evidence in the checkout.
   Cite the two independently. If a necessary address, field or slot is
   unconfirmed, open a focused evidence issue before writing a body.
4. Write ordinary C or C++ against the shared headers. Follow the
   [seven source-quality rules](docs/source-quality.md). Keep existing
   third-party notices and add the attribution in [NOTICE](NOTICE) to each file
   containing text adapted from the Electronic Arts release.
5. Update the pull request with the function or header, the evidence for names
   and layout, and any unresolved references or assumptions. Ask for a
   [ledger change](docs/ledger-and-checks.md#request-a-ledger-change) where
   annotations, ownership or accepted names need correction.

## Review and check

The [pull-request guide](ci/README.md) lists eligible source paths and
limits. Submit regular UTF-8 `.c` or `.cpp` files under `src/` and `.h`,
`.hh`, `.hpp` or `.inl` files under `include/`. Keep ledger, checker,
generated metadata and documentation proposals in a maintainer issue or
a separately coordinated change.

Three comparison checks report on pull requests—**BFME II / source rules**
(G1-G8), **BFME II / Boat** (Visual C++ 7.1 match comparison), and
**BFME II / Inline virtual** (pending can land; a fresh failure blocks; a stale
failure triggers re-measurement)—alongside **BFME II / Admission** and
**BFME II / Landing**.

- **Ready source-only fork PRs** (1-8 eligible `src/` paths affecting at most 8
  translation units, passing current source rules, within daily limits of 250
  per author and 1,200 total (`BFME_ADMISSION_DAILY_*`)): admitted automatically, compiled on Boat, and
  squash-merged to `main` automatically when current source rules and Boat pass
  against current `main` with a clean merge and no landing hold.
- **Draft PRs:** source rules can run, while automatic Boat admission waits
  until you mark the pull request **Ready for review** (maintainer-started
  comparisons are separate).
- **Header PRs (`include/`):** ready fork pull requests changing `include/`
  (with or without `src/`, up to 60 files, passing current source rules) are
  admitted automatically under the wide daily budget (currently 30/author and
  120 total/day, `BFME_ADMISSION_WIDE_DAILY_*`). Boat compares all affected translation units, including
  transitive includers (narrow for at most 8 affected units; wide for larger
  eligible sets). Keep function bodies out of shared headers unless supported
  by retail evidence. Header PRs auto-land once **BFME II / Header rules** pass on current `main`
  (including member layout changes proven by a matching typed-access witness
  under H5); header PRs whose Header rules are held (not failed) wait for
  approval on that exact commit from a listed maintainer in
  `ci/landing/landing.json`.

Read the statuses to see who must act: **Admission** reports budget holds
(retried automatically), conflicts (update your branch and push), or maintainer
waits; **Boat** Details shows code refusals to fix (with first differing offset
and compiled instructions when available) versus unmeasured runner faults
(retried automatically up to twice before a maintainer hold); **Landing** names
any remaining merge hold.

A local Visual C++ 7.1 check is optional (see
[Checker inputs and methods](tools/README.md)), while running
`tools/gates/gate.py` locally on committed changes before pushing is strongly
recommended. Do not attach executables, game
assets, or byte or disassembly dumps to a pull request. Point to the address,
caller, slot, offset or other evidence that a reviewer can verify in
`baseline/game.dat`.

A numerically better result does not excuse a duplicate class, lost proof,
invented name or unexplained change in runtime behavior. Keep unsuccessful
bodies out of a source change. Add useful attempts to the pull request
description or an issue. Link any related entry in the [hard-case index](docs/hard_rows.md).
